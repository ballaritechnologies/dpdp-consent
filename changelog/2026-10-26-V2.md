## [Unreleased] - 2026-10-26
### Summary
Per-site consent regimes (Phase 1). A site can route visitors with `dpdp` (everyone gets the India DPDP flow) or `dpdp_gdpr` (India → DPDP, EU/EEA/UK → GDPR, everyone else and unknown locations → a configurable default group). `strictest_global` is reserved and returns "not implemented". Sites without a regime keep plain jurisdiction-map routing. The geo-routing endpoints are now tenant-aware in multi-tenant mode, so each site's own regime and profiles are used.
### Added
- `@consenti/utils`: `regime.ts` with `REGIME_IDS`, `REGIMES`, `resolveRegimeGroup()`, `GDPR_REGIME_COUNTRIES`, `RegimeNotImplementedError`, `isRegimeId()`, `isComplianceGroupId()`.
- `@consenti/types`: `Regime` type; `TenantSettings.regime` and `TenantSettings.regimeDefaultGroup`.
- `@consenti/api`: `RegimeService`, applied by `GET /api/v1/resolve-profile` and `GET /api/v1/profiles/auto/:locale`.
- `@consenti/api`: `?tenant=` on both geo-routing endpoints (honoured only with `multiTenant.enabled`, validated before use).
- `@consenti/api`: `regime` / `regimeDefaultGroup` on `GET/PATCH /admin/v1/settings`, plus `?tenantId=` to target a site (checked against the caller's allowed tenants). Regime changes are audit-logged as `settings:regime_updated`.
- `@consenti/api`: schema v3, a nullable `tenant_settings.regime_json` column (SQLite, PostgreSQL, MySQL). Mongo and the JSON store need no migration.
- `@consenti/api`: dashboard "Consent regime" card on the Settings page, with a site picker when there is more than one site. Locale keys in all six dashboard locales.
- `@consenti/api`: OpenAPI entries for `/v1/resolve-profile` and `/settings`, and a `TenantSettings` schema.
- `@consenti/api`: 48 tests in `src/__tests__/regime.integration.ts`.
- Docs: new guide `/guides/backend/consent-regimes`; public and admin route pages updated; `docs/legal-open-questions.md` started.
### Changed
- `@consenti/ui`: the widget sends `&tenant=<tenantId>` to `/resolve-profile` when its tenant isn't `default`.
- `@consenti/api`: PostgreSQL and MySQL v2 migrations now stamp version `2` explicitly instead of `SCHEMA_VERSION`, so an upgrade from v1 also runs the v3 step.
### Fixed
- Docs: the geo-routing FAQ said an unresolved country falls back to `general-privacy-consent`; it actually falls back to `opt-in`.
### Breaking changes
None. With no regime set, routing is unchanged; `?tenant=` is ignored unless multi-tenant mode is on.
### Migration
Automatic: SQL databases upgrade to schema v3 on the next start (one additive column).
