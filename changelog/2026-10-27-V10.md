## [Unreleased] - 2026-10-27
### Summary
Multi-site isolation, stage 3 of 3 (signing keys): each site other than `default` signs with its own key derived from `dataSigningHash`, so signatures, cookies, tokens and receipt pseudonyms made for one site don't verify on, or link to, another. Single-site servers are unchanged.
### Added
- `SiteKeys` (`utils/crypto.ts`): `for(tenantId)` is the site's signing key, `HMAC(dataSigningHash, "ijazat:site-key:v1:" + site ID)`, or `dataSigningHash` itself for `default`. `verifying(tenantId)` also accepts `dataSigningHash` for data signed before this change.
- Tests: per-site record and receipt signatures, receipt pseudonyms, ownership cookies signed with the old key, parental-consent tokens across sites, and `SiteKeys`.
### Changed
- Consent-record signatures, receipts, receipt visitor pseudonyms (`visitorRef`), ownership cookies, parental-consent tokens and IP hashes use the site's key.
- `ReceiptService.visitorRef(tenantId, visitorId)` takes the site. So do the `visitorRef` callbacks of `ParentalConsentService` and `ErasureRequestService`.
- `verifyConsent()`, `verifyOwnershipToken()` and `verifyParentalConsentToken()` accept a list of keys.
- `buildConsentRoutes()` accepts a `SiteKeys` in place of the signing secret.
- Docs: `docs/audit.md` section 2 status, `apps/api/README.md` (multi-tenant and signing), `docs/regimes.md`, v0.1 release notes, roadmap.
### Fixed
- An ownership cookie or parental-consent token issued for one site was accepted by any other site on the same server.
### Breaking changes
- `ReceiptService.visitorRef()` and the `visitorRef` constructor callbacks now take the site ID first.
- Multi-site servers: receipts and requests a non-default site wrote before this change keep their old pseudonym, so they no longer turn up in a search by visitor ID. They still list and verify.
- Multi-site servers: IP hashes for non-default sites change, so new hashes don't match old ones.
### Migration
None for single-site servers. Multi-site: keep `dataSigningHash` unchanged, because every site's key is derived from it. Rotating it invalidates all signatures.
