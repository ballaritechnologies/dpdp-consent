## [Unreleased] - 2026-10-27
### Summary
Site-scoped storage: the visitor-keyed storage methods take the site and filter on `tenant_id` in every driver. A service bug can no longer read, change or delete another site's consent record, history, visitor row or notice record through a visitor ID.
### Added
- Optional `tenantId` on `getConsent`, `updateConsent`, `deleteConsent`, `getConsentHistory`, `getVisitor`, `updateVisitor`, `deleteVisitor` and `getNoticeShownForVisitor`, on all seven drivers and on `ConsentRepo`, `VisitorRepo` and `NoticeRepo`.
- Tests: per-site reads, updates and deletes on every driver (`consent-storage.integration.ts`).
### Changed
- Consent, visitor and notice services and the admin consent and visitor routes pass their site to storage. The check for a visitor ID already held by another site still looks across sites, on purpose.
- MongoDB: `deleteConsent` removes all of a visitor's consent records, like the SQL drivers (it removed only one).
- Docs: audit section 2 (all gaps fixed), API README, v0.1 release notes (schema v4; multi-site limitation removed), roadmap.
### Fixed
### Breaking changes
- Custom `StorageAdapter` implementations: the visitor-keyed methods above receive an optional last `tenantId` argument and should filter on it.
