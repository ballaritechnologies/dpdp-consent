## [Unreleased] - 2026-10-27
### Summary
Deleting a site now deletes its data. `DELETE /tenants/:id` and `StorageAdapter.deleteTenant()` remove everything stored for the site, on every driver, plus its profile files. Before, only the site row was removed. On PostgreSQL and MySQL the delete failed outright once the site had any data, and on the other drivers the data was left behind.
### Added
- Tests: deleting a site on every driver removes its consent records and history, visitors, notice records, receipts, audit log, API keys, templates and settings, and leaves other sites' data alone (`consent-storage.integration.ts`). Through the admin API, the profile files go too (`tenant-isolation.integration.ts`).
### Changed
- `deleteTenant(id)` deletes, in one transaction where the driver supports it: consent history, consent records, notice records, visitors, the audit log, profiles, entity records (receipts, requests, incidents and the like), API keys, settings, consent and UI templates, then the site. Users and roles are server-wide and stay. Users limited to the deleted site keep its ID in `allowedTenants`, so they gain no access to other sites.
- `DELETE /tenants/:id` validates the site ID, returns `404` for an unknown site, and removes `<profiles>/<site id>/` after the database delete.
### Fixed
- Deleting a site that had data failed on PostgreSQL and MySQL with a foreign-key error, and silently kept the data on the JSON, SQLite and MongoDB drivers. The dashboard's delete dialog already said "all associated data will be permanently removed".
### Breaking changes
- Custom `StorageAdapter` implementations: `deleteTenant()` must delete the site's data, not just the site.
### Migration
None. Profile copies uploaded to S3 (`s3Api`) are not removed; delete `profiles/<site id>/` in the bucket by hand if you use it.
