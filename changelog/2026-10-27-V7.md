## [Unreleased] - 2026-10-27
### Summary
Phase 9: the `strictest_global` regime (everyone gets the DPDP flow, hardened with GDPR-side protections) and an adapter interface for registered DPDP Consent Managers, with a development mock. Ijazat is not a Consent Manager.
### Added
- `@consenti/utils`: `regimeHardening`, `hardenProfile`, `STRICTEST_MAX_EXPIRY_DAYS` (365), `STRICTEST_GPC_ITEM_PURPOSES`.
- `strictest_global`: routes every visitor to `opt-in-dpdpa`; `/resolve-profile` and `/profiles/auto/:locale` return/apply a `hardening` block (GPC honoured for advertising items, consent expiry capped); the widget applies it (also on a cached resolution); the server refuses advertising items on every write carrying GPC.
- `ConsentManagerAdapter` interface (`compliance.consentManagers`), `ConsentManagerService`, `MockConsentManager` (development only); public route `POST /v1/consent-managers/:adapterId/notify`; admin route `GET /consent-manager-artefacts`; server event `consent_manager:event`; artefacts stored as `cm_artefact` entities with receipts (source `consent_manager:<id>`).
- Dashboard: "Strictest of both, for everyone" in Settings → Consent regime (six locales).
- Docs: `docs/consent-managers.md`, docs-site guide `/guides/backend/consent-managers`, regime guides, OpenAPI, events and route references; legal questions Q-R5, Q-M1 to Q-M3.
- Tests: `strictest-and-cm.integration.ts`, regime and profile-resolver tests.
### Changed
- `strictest_global` is accepted by the settings API (was `501`); `resolveRegimeGroup('strictest_global', …)` no longer throws.
- Receipts accept explicit decisions, source and notice version (for Consent Manager artefacts).
