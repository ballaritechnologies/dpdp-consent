## [Unreleased] - 2026-10-27
### Summary
Multi-site isolation, stage 1 of 3 (public API): with `multiTenant.enabled`, public requests are recorded under the site they name, one site's consent records, visitors and profiles are invisible from another, and unknown sites are rejected instead of filed under `default`.
### Added
- `TenantServices`: profile, consent, visitor and notice services built per site (bounded cache, `default` never evicted); `createConsenti()` returns `servicesFor(tenantId)`.
- `publicTenantResolver`: a public request's site from its `ck_` API key or `?tenant=`; unknown or malformed sites get `400`.
- `HttpError` for safe status-and-message errors under `withErrorHandler`.
- Widget: every public API call (consent, parental consent, TCF/GPP status) sends `?tenant=` for a non-default site; `resolveParentalConsent()` takes `tenantId`.
- Tests: `tenant-isolation.integration.ts` (through `createConsenti`).
### Changed
- `ConsentService` and `ProfileService` treat another site's records as not found on every lookup by ID.
- Public consent and profile route builders accept a service or a per-site factory.
- Retention and deletion-request services take the site when they act on consent records.
### Fixed
- `DELETE /consent/:visitorId` sent for one site could erase another site's consent record and visitor row.
- A visitor ID already used by another site could be taken over (visitor row updated, consent written); now refused with `409`.
- `GET /profiles/:tenantId/:group/:locale` and the version-file route built file paths from unchecked URL parts; they are now validated, and single-site servers only serve the default site.
### Breaking changes
- Multi-site servers: a public request naming an unknown site (`?tenant=`) now gets `400`.
- `ErasureRequestService` and `RetentionService` constructor callbacks take the site ID.
### Migration
Multi-site deployments: make sure each site's widget sets `core.tenantId` (or `api.tenantId`). Records written before this change were all filed under `default`.
